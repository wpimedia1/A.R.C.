# Capability delta: Day 1 → November 4, 2026

## What this comparison establishes

The project changed from a crisis-deliberation dashboard into an evidence-linked, agent-operated **software mission simulator**. Saved executions establish bounded planning, validated work, charging, daylight holds, conditional water accounting and continued survey operations. They do **not** establish physically reliable autonomous colonization, qualified robotic construction, or complete verification of the current working tree.

“Day 1” means the earliest recoverable repository baseline: **44bd845ad86a7349cfbd9a450929ffd75e40ae61**, October 27, 2026. It contains 35 tracked files. This audit does not reconstruct work before that commit or independently authenticate MetroDesk's history. “Today” includes the uncommitted workspace, not just HEAD **31e0e42**. Before writing these audit documents, Git reported **48 modified tracked entries and 75 untracked entries**. Those counts do not explain or validate a chat's “40k changes” indicator.

Audit method: local Git/source inspection, saved reports, JUnit results and **read-only SQLite queries**. No tests, servers, Docker operations, model calls, recordings or renders were started. Application code and mission data were not changed. Machine-readable findings and report hashes: [capability-delta-evidence.json](capability-delta-evidence.json).

Status terminology:

- **VERIFIED:** the named behavior has retained execution evidence, within the explicitly stated run/build scope. It does not mean the entire subsystem is complete.
- **IMPLEMENTED / UNVERIFIED:** code exists, but the claimed current integrated behavior lacks adequate execution evidence.
- **PARTIAL:** a useful subset exists, with a material missing integration, input or verification boundary.
- **MISSING:** no implementation establishes the claimed capability.
- **BLOCKED:** a named external dependency prevents execution. This audit does not classify ordinary unfinished engineering as an external block.

Day-1 statements below describe inspected source, **not independently rerun historical functionality**. Baseline paths can be recovered with `git show 44bd845:<path>`.

## Evidence conflicts that must not be concealed

1. **Older failure versus later conditional pass.** STATUS.md, UNFINISHED-FEATURES.md and WATER-MODEL-REVIEW.md still describe the earlier failed water run. The later engine-11 report records a software pass after adding D21 conditioning/reserve rules. Both runs remain evidence; the later one does not retroactively turn the earlier failure into a pass or validate the underlying physics.
2. **Acceptance reports do not exactly match today's source.** Engine-11 final and power-loss report hashes match **35/37** recorded backend files; `planner.py` and `store.py` differ. The later continuation matches **36/37**; `store.py` differs. `local-verification.json` matches **28/36** recorded files and explicitly carries pending engine-11 status. A blanket “current code fully verified” claim is unsupported.
3. **Tests are version-specific.** The older Windows XML has 147 tests; the later PostgreSQL XML has 156. The 156 count is confirmed in the retained log/XML, but there is no matching complete current-tree manifest attached to that test output. These counts cannot be used interchangeably or as proof of complete product acceptance.
4. **Provider identity is not physical validity.** Saved authenticated retrieval checks support that real responses existed and matched recorded public tool outputs. This audit did not issue fresh retrievals, inspect the Meta developer billing panel or establish hardware viability. The historical retrieval audit also retains one 404 and three records without retrievable IDs; those four remain unverified.
5. **Presentation improvement is not established by production effort.** New navigation/3D and rendered video assets exist. The rejected video and unfinished usability acceptance prevent a claim that the original judging-quality objective was delivered.

## Defensible capability claim today

**An implemented, partially verified agent-operated mission simulator can assign and execute bounded work against configured constraints and retain provider, decision, source and outcome records. Saved runs demonstrate this workflow. It has not established physically reliable autonomous outpost construction/colonization, a calibrated water/thermal/terrain system, complete default-fleet repair/offload, or a fully verified and accepted current release.**

The material delta is operational software and inspectable records. The material gaps are engineering completeness, default-mission integration, current-build acceptance and accepted presentation quality. Change volume does not resolve those gaps.
